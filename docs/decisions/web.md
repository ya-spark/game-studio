## Web and app differ on purpose (owner, 2026-11-21; supersedes earlier text where it differs)
- **Web is all free, all open, ad-funded.** Every rung of the trail is open; the visitor follows the suggested sequence or skips to anything. Opening a rung can show an ad. No purchases, no coins, no profiles or parent area on the web.
- **Web progress IS saved, in the browser only** (local storage on that device: trail stars, skills, streaks). Never sent anywhere, never moved to or from the app; the privacy text must say so. This supersedes "progress is not saved on the web" (2026-11-15).
- **Web ads:** AdSense for web, now including rewarded and interstitial ads and breaks in long play where they do not disturb the player (the earlier "no interstitials or rewarded ads on web" is replaced). Research 2026-11-21: Google's web game ad formats (the Ad Placement API, `adBreak`, rewarded) are the "H5 Games Ads" product, a closed beta with an application; the AdSense tag has a child-directed treatment switch, but eligibility of child-directed games for these formats is NOT confirmed and must be checked before Scout and Ranger use them. Needs the owner's AdSense account and approval.
- **App (purchases exist):** any rung can be opened by a purchase (Full Unlock) or, without one, by a rewarded ad. Extra packs open by purchase, coins or an ad, depending on the pack. **Coins apply only where Play Games sign-in exists**, so the balance can be saved with the player. This changes the 2026-11-09 and 2026-11-15 rules ("learning content is bought with real money only", "coins never buy learning content"): the Families policy and child-directed ad rules for Scout and Ranger have to be checked before it is built. The daily release goes away in favour of this. Not built; spec first.
- **Play Games on the web: not possible without a server.** Google documents the web flow only as server-side (a linked web app in Play Console and a server that exchanges an auth code for a token); a client-only browser sign-in was not found. A server breaks the no-backend rule, so web leaderboards and achievements wait for the backend the owner mentioned ("once we have the backend").
- **App-only for now:** purchases and coins, profiles and the parent area, Play Games sign-in, leaderboards and achievements. The owner left notifications unticked, meaning the web would get them too (browser notifications); asked again, not decided.
- **Keyboard (owner, 2026-11-21):** every game, in the app and on the web, can be played with a keyboard. All new games get it from the start; the existing games follow later (queued).
- **Web layout (owner, 2026-11-21):** web games are laid out for the web (different layout from the app at wider widths), **for new apps and games from now on; the existing apps are not changed**. The template has the helpers and the rule (`lib/ui/layout/responsive.dart`, `docs/WEB_LAYOUT.md`: compact, medium and expanded window classes). Existing apps and the games already on the web keep their current layout.
- Web notifications (owner, 2026-11-21): browser notifications are to be built for the web (reminders and review nudges). Open technical limit: with no backend, a browser cannot be woken to show a reminder when the site is closed (that needs a push server); what a client-only version can do is to be confirmed in the spec (W5).

## Games-first web flow (owner, 2026-11-21; spec W6 in `docs/FEATURE-SPECS.md`)
- The web landing page shows the games only. The year is asked once (the first time a game is opened), saved in the browser and changeable from a chip in the header; changing it makes the new year active, higher or lower. Topic is optional: the default is the first topic of the year not marked "I know this". There are three states (new, practising, known); `known` applies to every game, is reached through a 5-question "prove it" check (4 right to pass) and can be undone. When all are known the page offers the next year.
- All Craft games work for all years and topics (sorted, not filtered): Scout first for Years 0 to 6, Ranger for 7 to 10, Champion for 11 to 12, the rest below. Mind games sit in their own row at the bottom. Each Craft web build includes the free packs of all three Craft apps, merged at build time from the checkouts (nothing committed to the public repo). A game that cannot run a topic proposes other games that can (never the Quick quiz; owner, 2026-11-21, supersedes the earlier fallback).
- In a game the user can switch game and topic and open Learn; the bar is the existing one with new options. Learn is the route `#/learn/<subject>/<year>/<topic>` (Quick quiz first, teaching later); `#/quiz/...` stays as an alias. Progress is one JSON blob in the browser (`amc.state`, versioned, unknown topic ids ignored), one user per browser, never sent anywhere. This builds on the web-progress-is-saved decision above; the README line "nothing is saved" is out of date.
- No title bar inside a game (owner, 2026-11-21): new games do not draw their own bar with the game's name; the web bar already shows "Game: <name>" and a second bar is distracting. The game gets the whole play area, with small overlay controls. Existing games keep their `AppBar` until changed for another reason (the web shell cannot remove it without changing the apps). Rule added to `game-factory/CLAUDE.md`.
